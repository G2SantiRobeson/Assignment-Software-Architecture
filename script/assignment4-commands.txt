Assignment 4 - Grupo 7 - operational commands (PowerShell, repository root)
Requires Docker Desktop Linux containers, Compose >= 2.24.4, curl.exe and PowerShell.
Kubernetes additionally requires kubectl and k3d 5.8.3 or Minikube.
No report or presentation is generated by these scripts.

INITIALIZE ONCE
  ./script/edge.ps1 init
Preserves .env credentials, appends a random SECRET_KEY_BASE if absent, generates
tmp/edge/tls/tls.crt and tls.key. Neither .env nor generated secrets are committed.
APP_HOST in .env defaults to app.localhost. Re-run init after changing the hostname.
Browsers need the certificate trusted locally; curl can use --cacert directly.
For custom domains add 127.0.0.1 <APP_HOST> to the local hosts file.
For app.localhost, curl and the test container resolve it without modifying hosts.

FOUR DEPLOYMENTS (run one configuration per project at a time)
  ./script/edge.ps1 up single
  ./script/edge.ps1 up proxy
  ./script/edge.ps1 up full
  ./script/edge.ps1 up scaled
  ./script/edge.ps1 status scaled
  ./script/edge.ps1 down scaled
Single: http://localhost:3000. Others: https://app.localhost (HTTP redirects).
Before switching variants use down for the old variant. Named volumes persist.
Never use down -v unless intentionally deleting data.
APP_PORT, HTTP_PORT, HTTPS_PORT and UPLOADS_PATH are configurable in .env.
Existing Assignment 3 compose.yaml/compose.cache.yaml/compose.search.yaml/
compose.full.yaml remain standalone development entry points on port 3000.

Equivalent direct command (after init):
  docker compose --env-file .env -p book-reviews-a4 -f compose/compose.scaled.yaml up --build -d --wait --wait-timeout 240
The prepare service runs migrations once before web replicas, and initializes a
missing search index. edge.ps1 also runs prepare explicitly after rebuilding.
On an existing stack, pause writes before manually rebuilding the search index:
  docker compose --env-file .env -p book-reviews-a4 -f compose/compose.scaled.yaml exec web bin/rails search:reindex

STATE AND STATIC FILES
Sessions: PostgreSQL in single/proxy; the existing Redis in full/scaled, database 1,
separate namespace, one-day TTL, AOF persistence, no eviction. Redis DB 0 remains
the Assignment 3 cache. Cache/search retain their PostgreSQL fallbacks. Readiness
requires PostgreSQL and, for Redis sessions, Redis; /up is process liveness.
SECRET_KEY_BASE must be identical for all replicas. There is no sticky routing.
For database sessions, periodically run bin/rails db:sessions:trim.

Book and author forms accept original PNG/JPEG/WebP files, maximum 5 MiB by default
(MAX_IMAGE_BYTES). Active Storage metadata is in PostgreSQL; binary content lives
in the shared uploads volume at UPLOADS_PATH. Changing UPLOADS_PATH remounts the
same named volume. Images are public, unguessable /uploads/<key>.<extension> URLs.
Replacement produces a new key. Temporary multipart files do not persist state.
Active Storage direct-upload routes, analyzers and previews are disabled; purge
jobs run inline so they cannot be lost in a replica-local background queue.

Traefik is the only published entry point for proxy/full/scaled. Rails speaks HTTP
internally and does not terminate TLS. Traefik discovers all healthy web replicas.
Traefik OSS does not natively read files or cache response bodies. /assets and
/uploads route to a small Rack/Puma static origin in the SAME built image, with
read-only uploads. Cache-Control immutable, ETag/Last-Modified and 304 responses
provide HTTP client caching; this is not an in-Traefik response-body cache plugin.
Rails serves assets/uploads itself when RAILS_SERVE_STATIC_FILES=true (single).

KUBERNETES / K3D
Install k3d into PATH and pass -K3d k3d, or place k3d.exe in tmp/tools.
Pinned official Windows download (verify SHA256 with the release checksums):
  https://github.com/k3d-io/k3d/releases/download/v5.8.3/k3d-windows-amd64.exe
  https://github.com/k3d-io/k3d/releases/download/v5.8.3/checksums.txt
  ./script/kubernetes.ps1 create
  ./script/kubernetes.ps1 deploy
  ./script/kubernetes.ps1 status
Access: https://app.localhost:8443; HTTP port 8080 redirects to HTTPS.
The script uses the explicit context k3d-book-reviews-a4 and preserves existing
k8s/secret.yaml. It builds/imports the image, prepares the database with one Job,
applies an ignored generated overlay and waits for all Deployments, then reindexes.
Base resources reuse the existing namespace, PostgreSQL PVC and Redis/OpenSearch.
Rails Service is ClusterIP; Traefik Ingress resolves its ready pod endpoints.

There are separate PVCs for PostgreSQL, Redis, OpenSearch and uploads.
The uploads claim is ReadWriteOnce, shared by all Rails pods and the static origin
on ONE labelled node. RWO is not ReadWriteOncePod. The script rejects multi-node
clusters: migrating there requires RWX storage or an object-storage implementation.
Replicas tolerate loss of an application pod, not loss of this local storage node.

MINIKUBE ALTERNATIVE
  minikube start -p book-reviews-a4 --driver=docker --cpus=4 --memory=6144
  ./script/kubernetes.ps1 deploy -Context book-reviews-a4
  kubectl --context book-reviews-a4 -n book-reviews port-forward service/book-reviews-traefik 8080:80 8443:443
The verification uses the same local URL while port-forward is running.
If OpenSearch reports vm.max_map_count, set 262144 in the local Linux node.

VERIFICATION (creates uniquely named author/book records with uploaded images)
  ./script/edge.ps1 test
  ./script/verify_edge.ps1 -Deployment single -BaseUrl http://localhost:3000
  ./script/verify_edge.ps1 -Deployment proxy
  ./script/verify_edge.ps1 -Deployment full
  ./script/verify_edge.ps1 -Deployment scaled -Failover
  ./script/verify_edge.ps1 -Deployment scaled -BaseUrl https://app.localhost:8443 -KubernetesContext k3d-book-reviews-a4 -Failover
Pass -ProjectName if using a different Compose project. Evidence is written under
results/verification. TLS verification uses the actual generated certificate.
Failover stops one Compose replica (restored in finally), or deletes one Kubernetes
pod (Deployment replaces it), records convergence, then requires 30 successful
dynamic reads and an existing upload. Logs include X-App-Instance distribution.
Docker's health state plus Traefik /ready probes exclude unavailable replicas.
The verifier also checks a real Redis cache hit, shared session keys and the actual
search backend with assignment4:verify_dependencies.

LOAD TESTS
Complete sequential comparison (40 cases, about 3h20 plus preparation):
  ./script/load_matrix.ps1 -PauseK3dCluster book-reviews-a4
The existing book-reviews:assignment4 and grafana/k6:1.6.1 images must be available.
The script explicitly scales Rails to one, runs the full matrix, then scales to
three and repeats it. PostgreSQL/Redis/OpenSearch/uploads remain the same.
PauseK3dCluster is optional; it stops that local cluster to avoid resource
contention and restarts it in finally. Avoid other workloads during measurement.
It does not build images or run concurrent load cases.
To resume an interrupted run, pass the same parameters and its results directory:
  ./script/load_matrix.ps1 -ResultsDir results/matrix-YYYYMMDD-HHMMSS -PauseK3dCluster book-reviews-a4
Check progress from another PowerShell terminal:
  ./script/load_status.ps1 -ResultsDir results/matrix-YYYYMMDD-HHMMSS
Only validated completed.json cases are skipped. Incomplete attempts are renamed
and preserved. matrix.json records progress/failure and comparison.csv contains
measured timing summaries after all cases complete. Keep the machine awake and
Docker running. Abruptly killing PowerShell cannot run cluster cleanup; if needed:
  ./tmp/tools/k3d.exe cluster start book-reviews-a4

Individual deployment measurements:
  ./script/load_test.ps1 -Deployment full
  ./script/load_test.ps1 -Deployment scaled
Run these after starting the matching deployment, sequentially on the same machine.
Full (one Rails) versus scaled (three) holds Redis/OpenSearch/Traefik constant.
The required bare single deployment can also be measured:
  ./script/load_test.ps1 -Deployment single -BaseUrl http://localhost:3000
Each command runs counts 1,10,100,1000,5000, for each endpoint, each in 300 seconds.
Counts mean total requests during 5 minutes, not concurrent users or requests/sec.
One complete deployment matrix takes about 100 minutes plus preparation.
No extra HTML assets or redirect requests are counted. k6 checks exact request
count, status 200, no dropped arrivals, and the search backend where applicable.

Four targets reuse existing pages and an actual uploaded image:
  static:      /uploads/<actual-key>.png
  aggregation: /reports/top-selling-books
  search:      /book-search?q=architecture
  book:        /books/<actual-id> (detail reads PostgreSQL, including review average)
The load_data task adds an idempotent dataset (50 authors, 300 books, sales/reviews),
attaches an image, and reindexes; it does not delete existing application records.
Do not execute load_data concurrently with user writes or another load test.

Short infrastructure check (not a five-minute assignment measurement):
  ./script/load_test.ps1 -Deployment scaled -Counts 10 -DurationSeconds 10
One full five-minute measurement:
  ./script/load_test.ps1 -Deployment scaled -Counts 5000 -Endpoints book
Kubernetes:
  ./script/load_test.ps1 -Deployment scaled -BaseUrl https://app.localhost:8443 -KubernetesContext k3d-book-reviews-a4

Each results/<timestamp>-<deployment>-<endpoint>-<count>/ contains:
  run.json: parameters and timestamp
  samples.json: raw k6 durations/status codes, custom instance counters
  summary.json: k6 summary and threshold outcomes
  containers.jsonl / containers.csv: Docker CPU, memory, summed threads, PIDs
  processes.jsonl / processes.csv: per-process CPU%, RSS bytes, virtual bytes,
    threads, PID, start time, container identity and sample timestamp (Compose)
  requests.csv: one row per request, status, response time in ms, serving instance
  container-identities.jsonl: container names/images/services/resource limits
  metrics-metadata.json: process counter units and CPU interpretation
  threads.jsonl: total container threads, or /proc status in Kubernetes
  kubernetes-usage.jsonl: pod/container CPU and memory via metrics-server
  collector.log and traefik.jsonl: collection/edge evidence
The collector adds some overhead. k6 skips trust only for the local self-signed
certificate; functional verification separately checks certificate trust/SAN.
Compose process CPU uses deltas of Linux /proc/PID/stat user+system ticks divided
by elapsed time and CLK_TCK; 100% means one CPU, so values can exceed 100%.
The first observation has a blank CPU value because it has no prior interval.
RSS includes shared pages, so process RSS sums need not equal container memory.
Samples are taken about every five seconds plus collection time; very short-lived
processes between samples may not appear. The sampler shell/children are excluded.
The Docker PIDs field counts kernel tasks; explicit process thread counts are
captured separately. Collection starts before k6 and includes a final sample.
Kubernetes retains its metrics-server CPU/memory and process thread collector;
the per-process CPU/RSS extension and automatic matrix target Docker Compose.
Results stay ignored by Git and are not an assignment report or invented analysis.
